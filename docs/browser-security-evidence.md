## Гіпотеза й REG-XSS-01 (Для всіх)

Карта Description: docs/source-to-sink.md (основний потік Incident.Description; другий потік IncidentComment.Text там само). Гіпотеза source → storage → response → sink/context: значення з [textarea «Опис нового інциденту» → JSON-поле description] зберігається в [Incident.Description, колонка description у PostgreSQL], повертається через [поле description у відповіді GET /api/incidents/{id}] і передається в [document.querySelector("#description").innerHTML у browser-lab.js, функція load()] як [HTML context]; тому за умови HTML-подібного тексту браузер може інтерпретувати дані не як звичайний текст. Передумови: vulnerable state (scaffold 022455a, seed-коміт H2 `d6fd094`), БД скинуто командою `dotnet run --project src/SecureLab.Api -- --reset-database`, API запущено `dotnet run --project src/SecureLab.Api` (Development, http://localhost:5080); локальні користувачі: alice (автор запису), morgan (Analyst, привілейований глядач), bob (контроль). Guid запису з marker: `760803f8-1fe9-46fe-8020-376f5ba87e74` (інцидент Alice; marker-коментар Morgan `30000000-0000-0000-0000-000000000005`). Create/read: POST /api/incidents через форму «Створити й прочитати» на /browser-lab.html, потім GET /api/incidents/{id}.

Finding: актив: сеанс і дані користувача на origin `http://localhost:5080` (stored XSS у `/browser-lab.html`); передумови: HTML-подібний текст у `Incident.Description` або публічному `IncidentComment.Text` (marker-коментар Morgan, Id `…0005`, `IsInternal = false`), потерпілий з доступом до запису (Alice, Morgan) відкриває сторінку й завантажує інцидент; першопричина: недовірені дані інтерпретуються як HTML у клієнті (`innerHTML`, `browser-lab.js:10` і `:14`), а не сервер, який лише зберігає й повертає дані; safe DOM diff (commit `390eab2`): один helper `renderText(container, values, tagName)`: структуру задає код (`createElement`, `createTextNode`, `textContent`, `replaceChildren`), дані потрапляють лише в текстові вузли, sanitizer і blacklist-фільтри не застосовувались, бо форматований HTML у спільному scope не потрібен; retest: marker відображається як текст, `getAttribute("data-lab05-marker")` = `null`, Elements показує один текстовий вузол, `#comments` містить 2 публічні коментарі й 0 елементів `img`, звичайний текст і POST працюють; залишковий ризик: інші клієнти й майбутні sink-и, дані в БД лишаються HTML-подібними (це дані, не код), CSP лише другий рівень захисту і не замінює виправлення. Повторювана REG-XSS-01: після F5 `document.querySelector("#lab05-marker-target").getAttribute("data-lab05-marker")` = `null`; після завантаження інциденту Alice знову `null`; `2 0` (публічних коментарів і `img` у `#comments`); негативний контроль: у vulnerable state (`d6fd094`) очікується `executed`; очікування для fixed state: `null` і marker як видимий текст. Перед кожною перевіркою обов'язково F5, бо атрибут тримається до перезавантаження сторінки.

## CORS і REG-CORS-01 (Для всіх)

Прогноз (Етап 3, крок 1), заповніть до зміни policy:

| Сценарій                         | Чи доходить request до API?                                  | Чи може browser JavaScript прочитати response? | Чому                                 |
| -------------------------------- | ------------------------------------------------------------ | ---------------------------------------------- | ------------------------------------ |
| same-origin 5080 → API           | так                                                          | так                                            | та сама origin, CORS не потрібен     |
| simple GET 4173 → API            | так, запит надсилається                                      | ні, без валідних CORS-заголовків у відповіді   | browser SOP/CORS                     |
| simple GET 4174 → API            | так, запит надсилається                                      | ні, якщо origin не в allowlist                 | browser SOP/CORS                     |
| curl/.http → API                 | так                                                          | не застосовується                              | це не browser JavaScript, SOP не діє |
| preflighted 4173 → API («Добре») | спочатку OPTIONS; actual GET залежить від відповіді на нього | ні без успішного preflight                     | browser preflight і CORS             |

Команди запуску probes: з кореня репозиторію `py -3 -m http.server 4173 --bind localhost --directory demonstrations/cors-probe` і `py -3 -m http.server 4174 --bind localhost --directory demonstrations/cors-probe`. Policy — лише Development, один exact origin 4173; 4174 — контроль. Для «Задовільно» без AllowCredentials(); для «Добре» кінцевий стан містить `AllowCredentials()` (див. нижче). Порядок middleware: `UseRouting` → `UseCors` (лише Development) → `UseAuthentication` → `UseAuthorization` → `UseRateLimiter` → `UseDefaultFiles` → `UseStaticFiles`.

| Клієнт / простий запит | До policy                     | Fixed state                                                  | Status, ACAO, Console / доказ                                                                                       |
| ---------------------- | ----------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| Same-origin 5080       | працює без CORS               | працює без CORS                                              | `/browser-lab.html` читає API; CORS не потрібен                                                                     |
| Allowed 4173           | `Failed to fetch`, немає ACAO | `{status: 200, body: '{"status":"ready"}'}`                  | GET 200, `Access-Control-Allow-Origin: http://localhost:4173`                                                       |
| Disallowed 4174        | `Failed to fetch`, немає ACAO | `Failed to fetch`, `No 'Access-Control-Allow-Origin' header` | GET надіслано, ACAO відсутній; JS відповіді не бачить                                                               |
| Direct HTTP / curl     | читає відповідь               | читає відповідь                                              | `200` з тими самими security headers; для Origin 4173 є ACAO і ACAC, для 4174 і без Origin `Access-Control-*` немає |

REG-CORS-01: browser evidence і дві actual HTTP-відповіді для Origin 4173/4174: з Origin 4173 `curl.exe -i` повертає `HTTP/1.1 200 OK`, `Access-Control-Allow-Origin: http://localhost:4173`, `Access-Control-Allow-Credentials: true`; з Origin 4174 повертає `200` без `Access-Control-*`; у браузері 4173 читає response, 4174 ні. Перевірка порядку через читання 401 без cross-origin cookie: простий запит з 4173 до `/api/incidents` без credentials дає `401`, який прочитав JavaScript, отже CORS-заголовки додаються раніше за authentication/authorization. Пояснення різниці browser/direct HTTP: same-origin policy є правилом браузера для web-контенту; `curl` не браузер, тому читає будь-яку відповідь, але API однаково виконує автентифікацію, авторизацію й валідацію; відповідь на запит з 4174 доходить до API і виконується, браузер лише не віддає її JavaScript сторінки. REG-CORS-01 також перевіряє, що в `Program.cs` немає `AllowAnyOrigin`, `AllowAnyMethod`, `AllowAnyHeader`, `SetIsOriginAllowed` (`Select-String` порожній).

## Додатково для Добре та Відмінно

Другий flow IncidentComment.Text: потік описано в docs/source-to-sink.md (розділ 3). Public seed comment: Guid `30000000-0000-0000-0000-000000000005`, автор Morgan, `IsInternal = false`, текст — marker з `resources/lab05-marker.txt`; Alice бачить 2 публічні коментарі (було 1), внутрішні коментарі їй не повертаються (ЛР 4); похідні counts: `2 0` (коментарі, `img`) у fixed state. DOM до/після: до — `innerHTML` створює елемент `img` з `onerror`, після — один текстовий вузол усередині `<p>`. Єдиний safe helper і виклики для обох полів: `renderText(container, values, tagName)` у `browser-lab.js`; виклики: `renderText(#description, [current.description])` (текстовий вузол) і `renderText(#comments, тексти, "p")` (`<p>` з `textContent`).

Preflight з 4173 і 4174, OPTIONS → GET / blocked GET, exact origin/header/method: запит із заголовком `X-Lab-Cors-Probe` до policy: `OPTIONS` 405, actual GET не надсилається; після policy з 4173: `OPTIONS 204` з `Access-Control-Allow-Origin: http://localhost:4173`, `Access-Control-Allow-Methods: GET`, `Access-Control-Allow-Headers: x-lab-cors-probe`, потім `GET 200`; з 4174: `OPTIONS` без `Access-Control-*`, actual GET не надсилається, у Console помилка preflight. Висновок за статусом `OPTIONS` не робився, різниця лише в заголовках. Exact origin `http://localhost:4173`, метод `GET`, заголовок `X-Lab-Cors-Probe`.

Cookie-дослід 4173/4174/без AllowCredentials()/401 без входу: 4173 з Alice і `credentials: "include"` + `AllowCredentials()`: `200: […]`, Request містить `Cookie` і `Origin`, Response `Access-Control-Allow-Origin: http://localhost:4173` і `Access-Control-Allow-Credentials: true`; 4174 з Alice: запит із cookie дійшов до API, браузер не віддав response JavaScript; без `AllowCredentials()` (негативний контроль): `The value of the 'Access-Control-Allow-Credentials' header in the response is '' which must be 'true'…`, response недоступний JavaScript попри дозволену origin; приватне вікно без входу, 4173: `401` прочитаний JavaScript. Висновок: `credentials: "include"` на клієнті й `AllowCredentials()` на сервері діють лише разом; `AllowAnyOrigin()` разом з `AllowCredentials()` заборонений (виняток під час запуску). Кінцевий AllowCredentials() — лише Development policy для 4173 (commit `9c98895`), у Production policy не реєструється. Review XSS/CORS/CSRF/authorization — посилання на DEL-03: розділ «Короткий review XSS/CORS/CSRF/authorization» у звіті Короткий review XSS/CORS/CSRF/authorization; суть: CORS керує лише тим, чи може JavaScript іншої origin прочитати response, і не замінює автентифікацію, авторизацію й CSRF-захист (antiforgery реалізується в ЛР 6), не обмежує `curl` і не усуває XSS.

| Директива CSP   | Фактичні ресурси застосунку                                                              | Обране джерело / причина                                                                              |
| --------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| default-src     | HTML, JS, CSS, fetch до `/api/...` з `http://localhost:5080` | `'self'`: усі ресурси штатного клієнта same-origin                                                    |
| script-src      | зовнішній `browser-lab.js` (і app.js, якщо сторінка його підключає)                      | наслідує `default-src 'self'`; inline script і eval заборонені                                        |
| style-src       | зовнішній css (inline style відсутній)                                                          | наслідує `default-src 'self'`; inline style не використовується                                       |
| connect-src     | `fetch` до `/api/incidents` на тій самій origin                                          | наслідує `default-src 'self'`                                                                         |
| img-src         | зображень немає                                                            | наслідує `default-src 'self'`; зовнішнє зображення заблоковано                                        |
| frame-ancestors | вбудовування сторінки в iframe не потрібне                                               | `'none'`: сторінка не вбудовується в чужі iframe; не наслідується від `default-src`, задається окремо |

Місце зміни middleware: спільна middleware заголовків у `Program.cs` (поруч з `X-Content-Type-Options` і `Referrer-Policy`), заголовок ставиться до `await next(context)`; перша спроба поставити його після `next` дала `InvalidOperationException: Headers are read-only, response has already started` і обрив chunked-відповіді (`curl: (18)`), виправлено перенесенням блоку над `next`. Для `/scalar` у Development політика не застосовується. Enforcement: document 200 і фактичний CSP header `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'`; три сторінки flow (browser-lab.html, auth-lab.html) працюють без порушень; кероване порушення `new Image().src = "http://localhost:4173/x.png"`: `Refused to load the image … "default-src 'self'"`, у Network `blocked:csp`; `frame-ancestors 'none'` блокує iframe з 4173. CSP блокує inline `onerror` і для невиправленого sink, тому «sink виправлено» доведено лише через Elements і `null` на `390eab2`, а не через CSP. Для «Добре» докази report-only не обов'язкові (використано enforcement).

| Header / control       | Фактичне значення       | Ризик і межа захисту / policy rationale                                                          |
| ---------------------- | ----------------------- | ------------------------------------------------------------------------------------------------ |
| X-Content-Type-Options | `nosniff`               | браузер не вгадує MIME-тип; не захищає від XSS у дозволеному контенті                            |
| Referrer-Policy        | `no-referrer`           | URL не передається в Referer; не стосується CORS чи автентифікації                               |
| frame-ancestors        | `'none'` (у складі CSP) | сторінка не вбудовується в чужі iframe (clickjacking); не виправляє XSS і не замінює antiforgery |
